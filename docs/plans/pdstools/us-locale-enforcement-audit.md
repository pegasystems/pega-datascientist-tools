# US Locale Consistency Audit and Enforcement Plan

**Date:** 2026-08-03
**Branch:** 001-add-auc-confidence-intervals
**Status:** Analysis complete, implementation pending approval

## Objective

Establish a consistent numeric formatting policy across pdstools with two goals:

1. No output inconsistency for users running non-US system locales.
2. Enforce US locale formatting in pdstools outputs.

US locale in this context means:

- Decimal separator: `.`
- Thousands separator: `,`
- Percent formatting aligned with US-style punctuation

## Executive Summary

The codebase is already mostly US-style in output, but enforcement is not fully explicit in all rendering paths. The highest risk is not widespread locale logic, but inconsistent use of formatting abstractions and report-level direct formatting calls.

The audit found:

- A central formatting utility that supports locale selection (`en_US` default, `de_DE` optional).
- Multiple direct report formatting calls (`fmt_number`, `fmt_percent`) that bypass central policy control.
- A test that explicitly validates non-US formatting (`de_DE`), which conflicts with strict US-only output policy.
- Input parsing code in Impact Analyzer that is intentionally locale-tolerant (for ingestion robustness), which should be treated separately from output formatting.

## Scope and Method

Source-only audit was performed over `python/pdstools` and `python/tests`, excluding generated HTML and notebooks.

Primary checks:

- explicit locale usage (`setlocale`, `locale=`, `Intl.NumberFormat`, etc.)
- numeric formatting APIs (`fmt_number`, `fmt_percent`, `tickformat`)
- hardcoded format patterns using grouping/decimal punctuation
- decimal separator normalization logic in parsing paths

## Findings

### F1 — Output locale policy is not centrally enforced in all GT paths

**Severity:** High
**Goal impact:** A, B

`NumberFormat` is the intended central formatting abstraction, but GT application currently calls `fmt_number` and `fmt_percent` without an explicit locale guard at all call sites.

Reference:

- `python/pdstools/utils/number_format.py`

### F2 — Report templates contain direct formatting calls outside the central policy layer

**Severity:** High
**Goal impact:** A, B

Both key report templates include direct `.fmt_number(...)` and `.fmt_percent(...)` calls. This creates drift risk because formatting behavior can be defined in more than one place.

References:

- `python/pdstools/reports/HealthCheck.qmd`
- `python/pdstools/reports/ModelReport.qmd`

### F3 — Existing test contract includes non-US locale behavior

**Severity:** Medium
**Goal impact:** B

There is an explicit test that validates German locale output (`de_DE`). If policy changes to strict US-only output, this test and possibly related behavior must be intentionally changed.

Reference:

- `python/tests/utils/test_number_format.py`

### F4 — Plotly formatting is largely US-style already

**Severity:** Low
**Goal impact:** A, B

Most Plotly `tickformat` patterns use US-style punctuation conventions and are generally aligned with policy intent.

### F5 — Locale-tolerant input parsing exists and should remain a separate policy decision

**Severity:** Medium
**Goal impact:** A (indirect), B (if interpreted too broadly)

Impact Analyzer includes robust parsing for locale-formatted numeric/date input values. This is ingestion tolerance, not output formatting policy.

Reference:

- `python/pdstools/impactanalyzer/ImpactAnalyzer.py`

## Risk Assessment

### If we enforce US output without centralization

- Inconsistent behavior remains possible across report templates.
- Future contributors may reintroduce non-standard formatting through direct template calls.

### If we remove all non-US support indiscriminately

- We may regress user input ingestion from Excel/CSV exports using regional formats.
- We may conflate input tolerance requirements with output rendering requirements.

## Recommended Policy

### Output policy (recommended)

- Enforce US locale for all user-facing output formatting in reports, tables, and visual labels generated by pdstools.
- Keep punctuation deterministic regardless of host OS/user locale.

### Input policy (recommended)

- Keep locale-tolerant parsing for external source ingestion unless product requirements explicitly forbid it.
- Treat parsing tolerance as data-ingestion resilience, not as display locale behavior.

## Implementation Strategy (Phased)

### Phase 1 — Central policy hardening

- Make `NumberFormat` the single output formatting authority for tabular numeric formatting.
- Ensure GT rendering paths consistently apply US locale conventions.
- Document policy in developer guidance.

### Phase 2 — Report template convergence

- Refactor direct report-level `.fmt_number`/`.fmt_percent` usages to go through shared formatting policy helpers where practical.
- Keep minimal local overrides only where required for readability, with explicit policy comments.

### Phase 3 — Test contract update

- Decide whether to fully remove non-US output mode support in `NumberFormat`.
- If strict US-only is approved, update tests accordingly and remove contradictory expectations.
- Add policy regression tests asserting US punctuation under non-US runtime locale environments.

### Phase 4 — Broader sweep

- Review Streamlit pages and markdown renderers for direct f-string numeric formatting with implicit punctuation.
- Standardize or annotate deliberate exceptions.

## Proposed Acceptance Criteria

1. All user-facing numeric output in reports and GT tables uses US punctuation regardless of host locale.
2. Non-US runtime locale does not alter output punctuation in generated report artifacts.
3. Existing ingestion paths continue to parse common regional numeric/date input shapes unless explicitly deprecated.
4. Test suite includes explicit US-output invariance checks.

## Decision Log Required Before Code Changes

1. Confirm strict US-only output as product policy.
2. Confirm whether `de_DE` output mode should be removed or retained as internal utility capability.
3. Confirm that locale-tolerant ingestion remains supported.

## Recommended Next Step

Proceed with a targeted implementation plan and PR scoped to formatting policy centralization first, then report-template convergence, with staged test updates.
